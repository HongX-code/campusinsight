# 需求说明

## 1. 背景

高校学生在信息获取上存在三个具体痛点：

1. **入口分散**：通知发布在教务处、学工部、团委、研究生院、各学院等十余个站点，学生需逐个访问；
2. **阅读成本高**：单篇通知常见 800—3000 字，关键信息（对象、截止、材料）夹在流程性文字中间；
3. **判断成本高**：学生需要自行比对"我是不是符合条件""我该在什么时候交什么"，而通知不会替学生做这个判断。

由此产生的实际损失是：错过报名截止、提交材料不全、把时间浪费在与自身无关的通知上。

## 2. 目标与非目标

### 2.1 目标（初赛版本）

| 编号 | 目标 | 验收方式 |
| --- | --- | --- |
| G1 | 支持通知的人工录入与公开网页采集两种入口 | 两条链路均可完成"录入 → 解析 → 展示"闭环 |
| G2 | 把通知转换为结构化字段，并保留原文依据 | 每条字段可回溯到原文片段 |
| G3 | 结合用户画像给出三级匹配结论与理由 | 每个结论至少 2 条可读理由 |
| G4 | 支持基于已收录通知的问答并给出出处 | 回答附带通知标题 + 原文片段 |
| G5 | 支持待办与截止提醒 | 未来 30 天议程按剩余天数排序 |
| G6 | 关键技术指标可量化 | 评测脚本输出分类/日期/字段级指标 |

### 2.2 明确不做（放到后续迭代）

- 学校统一认证登录、教务系统对接；
- 全网自动爬虫、验证码与复杂反爬处理；
- 移动 App、微信小程序；
- 多智能体协作、自训练模型、知识图谱；
- 复杂推荐算法、多学校多租户、复杂权限与消息推送。

> 范围控制原则：**先保证闭环真实可用，再谈规模。**

## 3. 用户角色

| 角色 | 诉求 | 系统对应能力 |
| --- | --- | --- |
| 学生（主要用户） | 我该关注哪些通知？什么时候截止？需要交什么？ | 个性化匹配、待办、问答 |
| 学生干部/辅导员 | 通知要录入系统、解析错了要能改 | 通知录入、人工修正、复核状态 |
| 系统管理员 | 数据质量如何？哪些解析不可靠？ | 数据看板、置信度、复核率 |

## 4. 功能需求

### FR-1 通知中心

- FR-1.1 手动录入：标题、正文、发布时间、来源单位；正文自动清洗。
- FR-1.2 链接采集：粘贴公开网页 URL，抽取标题与正文；仅限白名单域名。
- FR-1.3 去重：同一通知重复录入时返回 409 并提示已有编号。
- FR-1.4 检索：按关键词（标题/正文）、分类、复核状态筛选，分页展示。
- FR-1.5 详情：展示原文全文与解析结果并列，便于核对。
- FR-1.6 删除：级联删除解析结果与待办。

### FR-2 AI 智能解析

- FR-2.1 分类：输出 9 类之一（学科竞赛/奖助学金/学术讲座/科研项目/志愿服务/社会实践/校园活动/实习就业/其他）。
- FR-2.2 字段抽取：报名截止、活动时间、适用对象、资格条件、报名材料、报名方式。
- FR-2.3 原文依据：每个字段附原文片段，供人工核对。
- FR-2.4 置信度与复核标记：低置信或缺关键字段时置 `needs_review`。
- FR-2.5 人工修正：可修改任意字段，保存后标记"已复核"并回写通知分类。
- FR-2.6 重新解析与批量解析。

### FR-3 个性化匹配

- FR-3.1 用户画像：姓名、年级、专业、兴趣方向。
- FR-3.2 三级结论：符合 / 可能符合 / 暂不符合。
- FR-3.3 判断理由：截止时间、适用对象、专业限制、资格条件、兴趣匹配各给出说明。
- FR-3.4 过期过滤：已过截止的通知不计入"符合"，并在理由中说明。

### FR-4 智能问答与时间管理

- FR-4.1 关键词检索已收录通知并给出 Top3 来源。
- FR-4.2 回答附通知标题、原文片段、来源链接。
- FR-4.3 检索不到时明确回答"未找到"，不编造。
- FR-4.4 通知可加入待办，状态支持待开始/进行中/已完成。
- FR-4.5 30 天议程按剩余天数排序。
- FR-4.6 **多轨道截止时间轴**：一条通知可产出多个截止节点，每个节点标注轨道
  （秋季/冬季等）、适用身份（博士研究生/硕士研究生/…）与办理事项；同一通知在不同身份
  下呈现的节点集合不同。
- FR-4.7 个人时间轴：按登录用户的年级自动归一到身份词，只返回本人需要办理的节点；
  学院审议、学院报送等管理节点不进入个人视图。
- FR-4.8 过期回看：刚过期的节点仍然展示并标出「已过期 N 天」，避免学生错过之后
  再也看不到发生过什么。
- FR-4.9 节点级接地：每个节点都必须能在原文定位到日期与对应事项，定位不到的剔除，
  不保留「看起来合理」的节点。
- FR-4.10 表格行的动作按单元格取：进度表类通知的办理安排写在表格里时，动作串只取
  「截止日期」右边那一格（工作内容），不得把「完成单位/星期/周次」等右侧列并入动作；
  同一格内「①… ②…」并列多件事时只取第一件。
- FR-4.11 表格行的身份按动作格判定：先看动作格里写明的执行者（「研究生在系统里上传
  送审论文」→ 学生侧），再退回「完成单位」列；动作里出现机构名仍判管理侧。
- FR-4.12 年份锚以标题为准：标题含「YYYY年」而页面发布年份与之冲突时，节点年份以
  标题为准（实测站点会把发布年份写错，导致同一通知的节点裂成两截）。

### FR-4A 结构化表格

- FR-4A.1 采集期保留列边界：HTML 表格按 `<tr>` 序列化，单元格之间写 `\x1f`
  分隔符，不得压平成一维字符串。
- FR-4A.2 列语义识别：按表头语义（学院/专业代码/专业名称/计划/电话/联系人/时间）
  给每列打标签，不按列位置猜；同一列名在不同通知里位置可以不同。
- FR-4A.3 字段补位：表格还原出的学院与专业补进专业限制，咨询电话补进联系方式；
  正文已明确写出的值优先，表格只补空缺，不覆盖。
- FR-4A.4 单元格级证据：补位字段的证据必须取自命中的那个单元格本身，
  不得用整行拼接串代替（拼装串无法在原文定位，会被接地校验判为编造）。
- FR-4A.5 列序接地（C11）：被采信的学院名/电话必须落在列数与表头一致的行里；
  列数不一致的值串列风险高于缺失，一律拦下。
- FR-4A.6 存量正文不做复原：旧版采集器压平入库的正文，列边界已丢失且不可复原
  （一行 `085600材料与化工1027-87164677` 既可切三段也可切两段，无外部信息可判定），
  只识别并标记 `needs_recollect`，界面提示重新采集；不提供「猜回来」的复原功能。

### FR-5 管理与统计

- FR-5.1 分类分布、解析覆盖率、平均置信度、复核完成率。
- FR-5.2 7 天内截止事项清单。
- FR-5.3 近 7 日录入趋势。
- FR-5.4 解析引擎来源统计（大模型 / 规则引擎）。

## 5. 非功能需求

| 编号 | 要求 | 实现方式 |
| --- | --- | --- |
| NFR-1 | 单机可运行，无需外部服务即可演示 | SQLite + 规则引擎兜底 |
| NFR-2 | 云端可切换，不改造业务代码 | SQLAlchemy 抽象 + 环境变量 |
| NFR-3 | 解析结果可审计 | 全字段 evidence + 置信度 + 复核状态 |
| NFR-4 | 采集安全 | 域名白名单、内网地址拦截、响应体积上限、超时 |
| NFR-5 | 单条失败不影响整体 | 批量解析逐条 try/except，模型异常自动降级 |
| NFR-6 | 页面在 1280—1920 宽度下正常显示 | 响应式栅格 + 断点适配 |
