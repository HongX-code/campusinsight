# 技术架构说明

## 1. 总体分层

系统为单体应用，四层结构，层间通过明确的函数边界交互，便于替换与单测。

| 层 | 职责 | 文件 |
| --- | --- | --- |
| 表现层 | 单页应用，REST 调用；Arctic Glass Design System（`app/static/css/style.css`）：9 视图、三档响应式，规范见 `docs/ui_design.md` | `app/templates/index.html`、`app/static/css/style.css`、`app/static/js/app.js`、`docs/ui_design.md` |
| 接口层 | 参数校验、路由、错误映射 | `app/routers/*`、`app/serializers.py` |
| 服务层 | 采集、清洗、抽取、匹配、问答、字段契约与规则校验 | `app/services/*` |
| 数据层 | ORM 模型、连接、建表 | `app/database/*` |

解析链路的服务模块（本轮补齐的三个模块列在最后三行）：

| 模块 | 职责 |
| --- | --- |
| `services/extractor.py` | 日期打分选截止、对象归一化、条件原子化、材料条目化 |
| `services/analyzer.py` | 解析编排、`_attach_literal_fields()` 挂载确定性字段、`_finalize()` 统一校验出口 |
| `services/matcher.py` | 七因子加权匹配：可解释的三级结论、专业 / 年级硬条件冲突判定、分项贡献分解 |
| `services/recommender.py` | 推荐编排：召回 → 排序 → MMR 重排，输出「为什么推给你」与跳过原因统计 |
| `services/genre.py` | 文体判别：事务通知 / 公示公告 / 新闻资讯 |
| `services/fields.py` | **结构化字段契约**：`FIELD_KEYS` 六个字面事实字段的确定性抽取，逐字段附原文 evidence |
| `services/reltime.py` | **相对时间解析**：`resolve_relative()` 结合发布时间把「本周五前」换算为 ISO 日期 |
| `services/validator.py` | **规则校验**：`audit()` 执行 C1—C11，输出 `{passed, issues, warnings, ok}` |

采集子层独立于解析链路，两者只通过"一条通知的 {title, content, publish_time}"交接：

| 模块 | 职责 |
| --- | --- |
| `services/collector.py` | 采集引擎：请求层（重试/编码/体积限制）、列表页解析、翻页、详情解析、附件抽取、栏目编排 |
| `services/crawler.py` | 单篇入口：用户粘贴一个链接时走这里，内部复用 collector 的请求与解析 |
| `services/genre.py` | 文体判别：事务通知 / 公示公告 / 新闻资讯，决定要不要抽报名类字段 |
| `scripts/real_audit.py` | 真实集质量审计：按文体分层复算指标，生成 `docs/real_audit.md` |
| `config/sources.json` | 采集源与选择器配置，新增高校只改配置 |
| `routers/sources.py` | 采集中心接口：源列表 / 抓取预览 / 勾选入库 |
| `scripts/crawl.py` | 命令行采集，支持落 JSON 快照（离线复现与举证） |

## 2. 关键数据流

### 2.1 采集 → 预览 → 入库

```
config/sources.json
   ↓ collector.crawl_source()
列表页 fetch_page → parse_list（配置选择器 / 结构打分兜底）
   ↓ parse_pagination()（只认真实链接，同目录才算翻页）
详情页 parse_detail（正文容器优先级 + 块级换行 + 数字碎片回粘）
   ↓ _extract_attachments()（正文内 + 附件区 + 全页）
{title, url, publish_date, content, attachments, content_type, chars}
   ↓ POST /api/sources/preview（标注 duplicate，不入库）
人工勾选 → POST /api/sources/import
   ↓ content_hash + source_url 双闸去重
notices(ingest_mode='crawl') → 解析链路（见 2.2）
```

采集与解析**解耦**：采集只负责"拿到干净正文"，解析只负责"读成结构"。
这样站点改版时只动 `config/sources.json`，抽取规则失效时只动 `extractor.py`，两边互不牵连。

### 2.2 录入 → 解析

```
用户提交 / URL 采集 / 栏目批量采集          ← 采集
   ↓
cleaner.clean_text()          归一化、去导航噪声、合并断行、保留章节标题
   ↓
genre.detect()                文体判别（闸门）：新闻资讯 → 不抽办理类字段（硬办理信号一票否决）
   ↓                          事务通知 / 公示公告 → 继续
classifier.classify()         词典加权打分 + 文体/志愿信号纠偏  → 分类 + 置信度
   ↓
extractor.extract()           抽取（含确定性字段）：日期打分选截止、对象归一化、条件从句、材料条目
   ↓                          ├─ fields.extract_structured()：年级 / 专业限制、报名开始、
   │                            活动举办时间、地点、联系人 / 电话 / 邮箱（字面事实，逐字段附 evidence）
   │                          └─ reltime.resolve_relative()：「本周五前」「三个工作日内」结合
   │                             publish_time 换算；缺发布时间则置空并标记待复核
   ↓
analyzer.analyze()            ① 大模型可用 → 提示词解析 → _validate_llm 校验
                              ② 不可用/失败 → _rule_result 规则结果
                              两条链路都过 _attach_literal_fields() 与 _apply_genre_gate()
   ↓                          —— 以上为「四层保护」：结构 / 文体 / 事实 / 兜底 ——
   ↓
_finalize()                   统一规则校验出口：validator.audit() 跑 C1—C11
   ↓                          硬异常进 issues → needs_review=true；软提示进 warnings
   ↓                          校验报告写入 result["checks"]
   ↓
notice_analysis 落库          14 类结构化字段 + evidence + deadline_source + checks
   ↓                          + confidence + needs_review + engine + genre + actionable
   ↓
人工审核（三态）             详情抽屉「规则校验与人工审核」区：通过 / 修正字段 / 驳回重解析
   ↓
展示                          字段 → 原文依据 → 校验报告逐条可见
```

文体闸门放在抽取之前、同时约束规则与模型两条链路，是为了避免"换上 MaaS 后同样的误报重现"。
下游也据此收敛：新闻稿不进入个性化匹配，待办接口直接返回 400。

确定性字段与大模型解耦：年级 / 专业限制、报名起止、活动举办时间、地点、联系方式这类**字面事实**
只由 `fields.py` 从原文捕获，不交给生成式模型输出；`_attach_literal_fields()` 挂载前逐条做证据接地校验，
证据对不上原文就整字段置空（宁缺勿造）。四层保护之外，`_finalize()` 是规则与大模型两条链路共享的
**统一校验出口**，任何链路都绕不过 C1—C11（详见第 5 节）。

### 2.3 匹配与推荐

匹配是**多因子加权 + 硬冲突否决**的两段结构，不是一串加法魔数：

```
用户画像(年级/专业/兴趣) + 全部已解析通知
   ↓ matcher.score_factors()
七因子归一化打分（权重和为 1）
   适用对象 0.28 ｜ 专业限制 0.14 ｜ 兴趣方向 0.20 ｜ 硬性条件 0.08
   时效紧迫 0.12 ｜ 内容新鲜 0.08 ｜ 信息可执行度 0.10
   ↓ 加权和 = fit(0~1) → score = 5 + fit × 93（5-98 分，规则加权匹配度 · 非录取概率）
   ↓ 硬冲突（学历/年级/专业明确不符）→ 直接判 level="no"，并把分数压到阈值以下
level(match/maybe/no) + score + factors[](逐项 raw/weight/contribution/state/note) + reasons[]
```

专业 / 年级 / 学历三类硬条件读 `grade_requirement` / `major_requirement` 归一化枚举做冲突判定
（`_check_grade_hard()` / `_check_major_hard()`）：命中冲突时不再给一个低分了事，而是直接判
`level="no"` 并写明"通知限定 X，你当前为 Y"。**否决项必须同时压分**，否则会出现"84 分却暂不符合"
的自相矛盾卡片；因此 `VETO_FACTOR` 把被否决的方案压进 20~45 区间。

几个刻意做成"中性而非零分"的因子，用来处理冷启动与缺失信息：

| 情形 | 处理 | 原因 |
| --- | --- | --- |
| 用户没填兴趣 | 兴趣因子 0.5 中性 | 不能把"没表态"当成"不感兴趣"，否则新用户全部降档 |
| 通知没有发布时间 | 新鲜度 0.5 中性 | 缺失不等于陈旧，扣分等于惩罚数据不全的源 |
| 资格够但兴趣完全不相关 | 结论降为「可能符合」 | 只关心竞赛的同学不该看到满屏"志愿服务 符合" |

推荐位在匹配之上再做**三段式**编排（`services/recommender.py`）：

| 阶段 | 做什么 | 关键约束 |
| --- | --- | --- |
| 召回 | 剔除未解析、新闻稿（`actionable=False`）、已截止、硬冲突、同标题重复副本 | 每个跳过项都计数进 `meta.skipped`，可解释"为什么没推这条" |
| 排序 | 按 `fit` 降序 | 相关性优先 |
| 重排 | MMR 多样性打散 | `MAX_PER_CATEGORY=2` 硬上限；多样性折扣只用于**打破近似同分平局** |

多样性折扣必须远小于典型 `fit` 差距（`DIVERSITY_LAMBDA=0.72`，折扣系数 0.12）。早期版本把
`fit × λ − 重罚` 一起算，等于把 89 分的第二条压到 76 分之后，`MAX_PER_CATEGORY` 形同虚设、
首屏顺序也不符合直觉——这是本模块最值得记的一处调试结论。

匹配与推荐都是纯规则运算，不调用模型：**结论必须可解释、可复现**。模型只负责把通知读成结构，
判断逻辑留在代码里；没有大模型时这条链路完全可用（`llm_available=false` 时推荐照样出结果）。

### 2.4 问答检索

问答走「召回 → 聚焦 → 作答」三段，全程离线可跑，大模型只是可选的润色层：

| 阶段 | 做什么 | 关键点 |
| --- | --- | --- |
| 预处理 | `_terms()` 去填充词（疑问/指代/人称/口语）、中文二元切分、同义词扩展 | 同义词**只加分不改门槛**，避免"保研"把整库都召回来 |
| 召回 | 标题命中 ×3.0、正文命中（封顶 6 次）×1.0、结构化字段 ×0.8，再乘 IDF 与长度归一 | 高频虚词（通知/报名）用 IDF 压权；长正文用 `1/√len` 归一 |
| 门槛 | 原词覆盖率 `matched / base_terms ≥ 0.5` | 宁可说"没找到"，也不用同义词凑答案 |
| 聚焦 | 领域词剔除误召回 → 最长标题片段锁定点名通知 → 按标题去重 | 防「国家奖学金」答成「国家励志奖学金」、防同一通知副本占两个名额 |
| 作答 | 八种意图（材料/截止/条件/联系方式/地点/方式/清单/通用）各自走结构化字段 | 字段为空时回落到原文小标题摘句，并如实写"原文未写明" |

两处容易答错、已单独处理的口径：

1. **清单类问题要分「能报 / 已截止」**：`list` 意图先剔除新闻稿（新闻稿不是可办理事项），
   再把有截止日期且已过期的排到后面；「有哪些…可以报名」只列未截止的，若一条都不剩，
   lead 改成「N 条都已过报名截止时间，下面列出原通知供你核对」，绝不在全过期时套用「尚未截止」。
2. **答案必须能被原文核对**：每条结论带 `[n]` 编号，`citation_check()` 校验编号不越界；
   大模型回答一旦编号越界或无编号，直接回退到结构化抽取回答，不带病输出。

引用列表同时带 `category` 与 `deadline` 字段，前端据此在引用卡片上直接标出「已截止」，
读者不必再回原文确认这条还能不能报。

### 2.5 人工审核闭环

校验报告落库后，详情抽屉的「规则校验与人工审核」区（`.check-panel`）把它逐条展示出来：
通过 N 项 / 拦截 N 项 / 提示 N 项，并给出首个硬异常说明。`PUT /api/notices/{id}/analysis` 支持三态：

| 动作 | `action` | 行为 |
| --- | --- | --- |
| 通过 | `approve` | `reviewed=true`、`needs_review=false`，复核说明追加「人工通过」 |
| 修正字段 | （空，带字段） | 覆盖 `AnalysisUpdate` 中的结构化字段，标记「已人工复核」 |
| 驳回重解析 | `reject` + `reject_reason` | 回退 `reviewed=false`、`needs_review=true`，说明写「人工驳回：…（需重新解析）」 |

驳回不把错误结果洗成"已审核"；重新解析并再次通过时，旧的驳回说明会被清理，
避免说明里同时留着"需重新解析"和"已通过"。至此形成
**解析 → 规则校验 → 报告落库 → 人工三态 → 重新解析** 的闭环，界面截图见 `docs/shot-review.png`。

## 3. 五个核心设计决策

### 决策一：日期抽取用"上下文打分"而非"取第一个日期"

通知里通常有 3—6 个日期（发布时间、报名起止、活动时间、公示时间、评审时间）。取第一个或最靠后的都会错。

做法是给每个日期候选按左右 32 字窗口内的线索打分：

| 线索 | 权重 | 例 |
| --- | --- | --- |
| 报名截止 / 申请截止 | +6 | "报名截止：11月20日" |
| 截止 / 截至 | +4.5 | "截至11月7日18:00" |
| 范围结束符（至/到/—/~）出现在日期左侧 6 字内，**且上下文有办理动词** | +5 | "报名时间为11月1日**至**11月20日" |
| 前提交 / 前将 / 前发送 | +3.5—4 | "于11月6日**前将**材料交至…" |
| 发布时间 / 发布日期 / 印发 | −5—−8 | "**发布时间**：2026-10-15" |
| 举行 / 举办 / 开幕 / 讲座 | −2.5—−5 | "报告**时间**：11月10日" |

范围结束符这一条在接入真实站点后补了前置条件：原先"公示期为X至Y""新闻网讯 10月30日至11月2日"
同样会 +5，把公示期、会期、活动期全推成报名截止。现在要求该范围所在行（含上一行标签）
出现报名/申报/提交/征集等办理动词，且不含公示期/会期/新闻导语等排除词；标签独占一行时语境向前多取一行。
这一处修正让开发集截止日期准确率 91.7% → 100%、召回 90% → 100%。

取最高分；同分取较晚日期（范围区间的右端才是截止）。得分 ≤ 0 则判定"未识别到截止日期"，而不是硬猜一个。

### 决策二：适用对象归一化为身份词

原始表述五花八门："全日制在校本科二年级以上（含二年级）学生""经学校认定的家庭经济困难的全日制本科在校生""2027届本科、硕士、博士毕业生"。

直接把这些句子当"适用对象"既不利于展示，也无法参与判断。系统将其归一化为最小身份词集合：`本科生 / 硕士研究生 / 博士研究生 / 专科生 / 毕业生 / 教师 / 师生 / 学生`。

归一化后，匹配逻辑只需判断"用户身份 ∈ 通知对象集合"，规则稳定且可解释；年级、专业等细分限制归入 `conditions`。

### 决策三：报名材料按"条目"抽取

早期版本用关键词命中（出现"报名表"就加一条），结果是"扫描通知附件中的二维码填写报名表"会被整句当成材料，而"国家奖学金申请审批表"因为词表里没有而漏掉。

改为条目抽取：

1. 先按章节切块，命中"材料 / 清单 / 附件"标题的整段纳入候选；
2. 括号注释、数量词（各一份、复印件、若干）、编号前缀先剥除；
3. 按顿号/逗号/和/及切分为条目；
4. 条目含动词（扫描、填写、发送…）或过长时，只取其中已知的材料名词；
5. 否则条目本身以"表/书/单/件/料/明/案/图/片/频/码/证…"结尾即认定为材料。

该调整把报名材料 F1 从 45.7% 提升到 85.7%。

### 决策四：截止时间存成"节点数组"而非"一个日期"

前三个决策都在「把单个字段抽准」这一层，第四个换了问题：**有些通知的时间本来就不是
一个点，而是一张网格**。

《关于2026年秋冬季博士、硕士学位授予及相关工作安排的通知》原文里，同一件事在秋季与
冬季各有一组日期，6 行「X月X日（秋季）和Y月Y日（冬季）」并行推进，共 14 个节点：

| 事项 | 秋季 | 冬季 |
| --- | --- | --- |
| 博士预答辩 | 7-02 | 10-08 |
| 硕士提交答辩意向申请 | 7-07 | 10-10 |
| 博士提交答辩意向申请 | 7-03 | 10-09 |
| 博士"答辩前检测" | 7-06 | 10-10 |
| 硕士"答辩前检测" | 7-08 | 10-12 |
| 学位答辩 | 9-29 | 11-24 |
| 各学院学位分会审议 | 10-08 | 12-02 |

单值 `deadline` 只能存一个，实测存的是 `2026-10-08`（博士预答辩）。后果有两个，
而且都不是"算得不准"能修的：

1. **这个日期对多数人是错的**。硕士生要赶的是 10-10 提交答辩意向、10-12 答辩前检测，
   不是 10-08。
2. **秋季整条轨道消失**。7 月的 7 个节点一个都没落地，秋季批次的学生收不到任何提醒。

所以把截止时间从"一个字符串"改成"节点数组"，每个节点带 `(轨道, 身份, 事项, 日期,
原文依据)` 五元组，抽取按分句做三元组绑定：

1. 按 `；/。/换行` 切分句（**不能按逗号切**，逗号是日期与事项的分界）；
2. 分句内按出现顺序取括号里的轨道标记，标记少于日期数时循环补齐；
3. 日期之后的尾巴里找「截止」或「前」，截出事项；没有截止词的句子（「各学院反馈
   《毕业生答辩登记表》至研究生院」）只要尾巴含办理动词也算节点；
4. 主语命中 `各学院/研究生院/学位办公室/培养办` 判为管理侧（`scope=admin`），
   否则按身份词归到 `博士研究生 / 硕士研究生 / 本科生 / 专科生`；
5. 事项串剥掉「有申请学位意向的」「被抽查评阅的」这类定语前缀，剥完不含动词的丢弃
   （「含民族」「详见相关学院官网通知」不是待办）。

输出经 `validator.py` 的 C10 逐节点回原文核对日期与事项，对不上原文的剔除并重排序号。
个人视图（`GET /api/timeline`）只取 `scope=student` 且身份匹配的节点——同一份通知，
博士生看到预答辩与评阅材料审核，硕士生看到答辩意向申请与评阅申请，学院审议两边都
不出现。

这一步的价值不在"多抽了几个字段"，而在**发现了单值数据结构本身装不下真实事实**。
单条通知内部怎么调算法都发现不了这件事，因为每条单独看都是"对的"。

### 决策五：表格在采集期就保留列边界

第四与第五个决策是同一个毛病的两种表现：**上游的数据结构装不下**下游真正需要的信息。
第四是"一个日期装不下多个节点"，第五是"一行文本装不下一张二维表"。

《关于我校2026年部分博士研究生（专项计划）补充报名的通知》里最贵的信息全在表格中：
学院 × 专业代码 × 专业名称 × 拟招生计划 × 咨询电话，5 行 5 列。但采集器原来的做法是
把 `BLOCK_TAGS` 里所有块级标签一视同仁地前后加换行，`<tr>` 与 `<table>` 都在名单里，
而行内 `<td>` 不在——于是 `get_text("")` 直接把格子拼成一段没有分隔符的长串：

```
拟招生计划咨询电话材料科学与工程学院      ← 表头末列与首行首列粘连
085600材料与化工1027-87164677            ← 代码/名称/电话三段粘连
1027-87218976                            ← 电话被挤成独立行，与学院错位
```

实测这条通知的解析结果：`major_requirement = []`（5 个学院、5 个专业全部没识别）、
`target = ['硕士研究生']`（**判反**，标题写明博士专项计划）、`contact.phone` 只有 3 个
且丢了 `027-` 区号。要强调的是：**这不是抽取器的错**。列边界在采集阶段就已经不存在，
下游再怎么改字段正则也补不回来——一维字符串里没有任何信息能说明"085600"是第二列、
"材料与化工"是第三列。

所以修在采集期，分三步：

1. **序列化**：`collector._table_to_text()` 把每个 `<tr>` 的直属 `td/th` 用 `\x1f`
   （Unit Separator）连接，行间用换行。挑 `\x1f` 而不是 `\t` 是有代价考量：
   `textutil._SPACE_RE` 会把制表符压成空格，列边界还没走到解析器就被抹平了；
   `\x1f` 不属于任何空白字符类，`clean_text()` 与 `normalize_text()` 都会原样放过。
   同时 `cleaner.clean_text()` 给含分隔符的行开了直通和"不参与短行合并"两个保护，
   否则一行只有一个「1」的表格数据会被碎片合并逻辑粘到上一行去。
2. **还原**：`services/tables.py` 按分隔符切回二维数组，用首行做表头，按语义给每列
   打标签（`college / major_code / major_name / plan / phone / person / date / detail`）。
   标签按**语义**匹配而不是按位置猜，因为不同通知的列序并不一样；`major_code` 的规则
   必须排在 `major_name` 前面，否则"专业代码"会被"专业"先吃掉。
3. **补位**：`fields.extract_structured()` 用表格还原出的学院与专业补 `major_requirement`、
   用表格电话补 `contact.phone`。**只补不覆盖**——正文里显式写"面向材料学院"比表里
   一列学院名更可信。补进来的证据必须取**命中的那个单元格本身**，不能把整行拼成一句：
   拼装串在原文里定位不到，会被 C5 判成编造然后整字段丢弃（这是第一版的真实失败）。

最后 `validator.py` 的 C11 做列序接地：被采信的学院名与电话必须真的落在某个单元格里，
且该行的列数与表头一致。列数一旦对不上，值会整体串列——把"拟招生计划"的 1 当成专业
代码、把专业名当成学院名，这种错比空着危险得多。

这一条顺带修掉两个同源缺陷：`PHONE_RE` 会从 URL 的 `t20250425_1326927.shtml` 里抠出
`1326927` 当电话（改为匹配前先抹掉 URL），以及正文只有「研究生院」「研究生专项计划」
这类机构名时，裸「研究生」会把受众兜成硕士研究生（改为先剥复合词，并让标题参与判定）。

**存量正文不做复原，这一点要说清楚。** 本能力上线前入库的通知已经被压平，一个 `\x1f`
都没有。早先这里写过一个 `recover()`，声称能按「重复出现的列宽模式」把压平的表格救回来；
压测之后发现它对自己声称要修的那类正文完全无效（它只在上一行本来就带分隔符时才动手），
而且会把电话拼到上一行末尾，拼出来的字符串在原文里并不存在，与 C11 的「逐格回放原文」
直接冲突。按「未验证不许写成已完成」的规矩，那段代码已删除，换成 `needs_recollect()`：
三种表格特征（六位专业代码、以「学院」结尾的单位名、带区号的电话）同现而 `\x1f` 缺席，
就判定为「压平存量」，在响应里置 `table_needs_recollect=true`，界面显示「需重新采集」。

删除而不是修好它，是因为复原在信息论上不成立：`085600材料与化工1027-87164677`
既可切成「代码 / 名称 / 电话」三段，也可切成「代码 / 名称 1027 / 电话」，
没有外部信息能判定哪种对。承认不可复原，比给出一个看起来能用的猜测诚实。

### 补充一（接决策五）：表格行的动作只取「工作内容」那一格

保住列边界之后又冒出一个新问题：**时间轴的抽取器原本只认识自然句，不认识表格行**。
`_action_from()` 拿到 `日期` 之后的尾巴就去找「截止」或「前」，找不到就一路截到行尾；
而表格行 `序号\x1f截止日期\x1f工作内容\x1f完成单位\x1f星期\x1f周次` 里，日期右边还有
四格。结果是动作串把「星期」「周次」一起吞进去：

```
改前：各学院返回毕业答辩登记表至培养处各学院星期三第二周
改后：返回毕业答辩登记表至培养处
```

这不是正则写得松，是**分句模型和表格不是一回事**。表格里「一列」才是一个语义单元，
用自然句的截断规则去切二维数据，必然要么吞掉右侧列，要么在格内的顿号处断在句子中间
（「各类型博士、硕士办理答辩手续」会被截成「各类型博士」）。

所以给表格行单独开一条路径 `_table_cell_action()`：按 `\x1f` 切格 → 找到日期所在的格 →
取它右边那一格作为动作来源 → 格内若并列「①… ②… ③…」只取第一件。同时 `_CLAUSE_SEP`
加入 `\x1f`，让 `_cut()` 在单元格边界就停下，普通正文不受影响（正文里没有 `\x1f`）。

身份判定也要跟着改。进度表类通知的「完成单位」列常写「各学院、各研究生」这种混合值，
只看这一列会把学生自己的事判成学院办理，个人时间轴上就消失了。`_role_of_table()` 因此
先看「工作内容」格里写明的执行者（「研究生在系统里上传送审论文」→ 学生侧），
再退回「完成单位」列；动作里出现机构名（「培养处下发…」）仍按管理侧处理。
顺带把 `培养处 / 学位办 / 校学位办` 补进 `_ADMIN_WORDS`——它们是「培养办 / 学位办公室」
的另一种写法，漏掉就会把机构待办推给学生。

### 补充二（接决策四）：年份锚以标题为准，不以发布标签为准

时间轴要把「7月2日」补成完整日期，得先定一个参考年。原来直接用页面上的发布时间，
实测踩到一个真坑：**站点自己把发布年份写错了**。

《【学位授予】关于2019年秋季博士、硕士学位论文答辩及学位授予等工作安排的通知》
页面标签写着「发布时间：2020-09-04」（URL 是 `/201909/t20190912_…`，标题写着 2019 年）。
按发布时间补年份，同一份通知的节点裂成两截：

```
改前：2019-07-10 / 2019-08-30 / 2019-09-11 / 2020-07-09 / 2020-08-30 / …
改后：2019-07-10 / 2019-08-30 / 2019-09-11 / 2019-07-09 / 2019-08-30 / …
```

标题里的「YYYY年」是编辑提炼过的强证据，常常还是全文唯一写明学年的地方；发布时间是
采集来的元数据，可能出错。所以 `_title_year()` 抽标题里的四位年份，与发布年不一致时
以标题为准，同时把 `infer_year()` 的基准日换成该年的 1 月 1 日，避免跨年阈值再判错一次。
标题没写年份就完全退回原逻辑——42 条真实通知里只有 1 条结果会变（《2027年推荐免试…招
生简章》，发布 2026-09-16，改后节点年份为 2027，正确），回归面极小。

## 4. 采集层：三个反直觉的实现细节

这三条都不是"设计得好"，而是"踩过坑之后不得不这样写"，也是接入真实站点后最先暴露的问题。

### 细节一：正文容器不能取"文字最多的那个"

多数教程式的正文抽取是"遍历所有 div，选文字最多的"。在校园 CMS 上这一定会错：
外层 `div.content` 把面包屑、「发布时间」、**浏览量**一起包进去，永远是最长的。

后果不是"正文多几行"这么简单——浏览量每次访问都自增，正文内容随之变化，
`content_hash` 每次都不同，同一条通知会被反复判为"有更新"。

现在的做法：按选择器优先级命中，命中的多个容器之间再用"包含关系 + 体量比"收敛：

```python
wrapped = any(node is not other and node in other.parents
              and text_len(other) < text_len(node) * 1.3
              for _, other in hits)
if wrapped:            # 它只是更精确容器的外层包装
    continue
```

### 细节二：数字不能在清洗阶段被当噪声删掉

CMS 常把数字、单位、日期分别包进 `<span>`，`get_text("\n")` 之后
「2025」「年11月20日」成了两行，「2」「人」也成了两行。
如果清洗阶段带一条"纯数字行是最长行/噪声行"的规则，这些数字会被静默删除，
原文变成「报名截止时间 2025年月日20:00」——截止日期整条消失，且没有任何报错。

修复分两步：`_node_text()` 只在 `<br>` 和块级标签处换行，行内元素直接拼接；
`_merge_fragments()` 再把残留的数字碎片粘回相邻行。

效果：正文数字不再残缺，截止日期恢复可抽取。真实集后来改用分文体口径衡量
（事务与公示类办理截止覆盖 20/24，新闻资讯误报 0/18），见 `docs/real_audit.md`。

### 细节三：翻页链接必须校验目录

「查看更多」在校园站点里既用于翻页，也用于跳到别的栏目。
如果只按文字匹配，「综合新闻」翻着翻着会漂到「理工资讯」，把无关通知收进来，
而每次请求都返回 200，日志上看不出任何异常。

规则：文案是「查看更多/更多」时，跳转目标必须与当前页**同目录**才算翻页；
另外对「下一页」等于当前页的情况直接判定到底，防止自环。

## 5. AI 可信性设计（四层保护）

| 层 | 机制 | 拦截的问题 |
| --- | --- | --- |
| 结构保护 | 强制 JSON Schema；分类枚举收敛（近义词映射回 9 类）；列表长度与类型校验；容错解析代码围栏 | 模型输出非 JSON、字段类型错乱、自造分类 |
| 文体保护 | `genre.detect()` 先判事务通知 / 公示公告 / 新闻资讯；判为新闻时报名类字段整体留空、`actionable=false`，规则与大模型两条链路共用这道闸门 | **「看起来合理、原文根本没说」的假字段**：把赛事会期、公示异议期、学科名词当成报名信息 |
| 事实保护 | `date_grounded()`：抽出的日期必须能在原文找到"YYYY年M月D日 / YYYY-MM-DD / M月D日"等形态；`evidence_grounded()`：证据片段前 8 字必须出现在原文 | **日期幻觉**、编造条件、编造材料 |
| 兜底保护 | 模型不可用/超时/异常 → 规则引擎；引擎来源写入 `notice_analysis.engine` 并在界面标注 | 服务不可用导致业务中断 |

事实保护命中时的处理不是"修正"，而是**置空 + 降置信度 + 标记待复核**：宁可少给字段，也不给错字段。
文体保护与前三层互补：前三层校验"抽出来的对不对"，文体层先问"这条通知该不该抽"。
42 份真实通知里，闸门在 18 份新闻稿上拦下 25 个假字段，误报率 0/18；
公示公告的日期不丢弃，只改标 `deadline_kind="异议截止"`，避免与报名截止混称。

**四层保护之外还有规则校验，统一表述为「四层保护 + 规则校验（C1—C11）」**——它不是并列的第五层，
而是对四层产出结果的再约束：四层管"模型输出能不能信"，规则校验管"结果本身是否自洽、是否 grounded 于原文"。
`services/validator.py` 的 `audit(result, text, publish)` 依次检查：

| 编号 | 检查项 | 处理 |
| --- | --- | --- |
| C1 | 日期格式与真实性 | 硬异常 |
| C2 | 截止 ≥ 发布时间 | 硬异常 |
| C3 | 报名起止顺序 | 硬异常 |
| C4 | 截止时间跨度合理（≤ 730 天） | 硬异常 |
| C5 | 证据片段原文接地 | 硬异常 |
| C6 | 截止日期原文可定位（相对时间换算走 `deadline_source="relative"`） | 硬异常，否则置空 |
| C7 | 活动时间与截止冲突 | 软提示 |
| C8 | 置信度偏低 | 软提示，不硬拦截 |
| C9 | 文体闸门字段泄漏 | 硬异常 |
| C10 | 时间轴节点原文接地（逐节点核对日期与事项） | 硬异常，剔除无法定位的节点 |
| C11 | 表格派生字段的列序接地（学院/专业/电话必须落在列数一致的行里） | 硬异常，值串列比空值更危险 |

返回值 `{passed, issues, warnings, ok}`：硬异常进 `issues` 并置 `needs_review=true`，软提示只进 `warnings`。
`analyzer._finalize()` 是规则引擎与大模型两条链路的**统一校验出口**，把整份报告写入 `notice_analysis.checks`，
换引擎不会绕过约束；前端 `.check-panel` 据此渲染通过 / 拦截 / 提示计数，并承接 2.5 的人工审核三态。

**界面层的可信性落点**：详情抽屉把 `checks` 报告渲染为 `.check-panel`（通过 / 拦截 / 提示计数 + 人工审核三态），
14 类字段与各自的「原文依据」绑定为一组 `.field-block`，避免证据块占整行打乱双列网格；
点击任一「原文依据」由 `jumpToEvidence()` 在通知原文中黄色高亮（`.content-box mark`）并滚动定位，
从而在界面上形成「AI 结论 → 结构化信息 → 原文证据」的完整闭环。设计变量、组件规范与截图检查要点见 `docs/ui_design.md`。

工程规模与验证口径：源码约 **22200 行**（Python 17300 + 前端 4841，其中 HTML 648 / JS 2415 / CSS 1778）、**51 个路由端点**
（含页面 `/` 与 `/api/health`，其中 JSON API 28 个）、**14 类结构化字段**（总控文档 8.2）、
文体 3 类、`deadline_kind` 7 类；端到端自检 **293 项全通过**（`tests/test_smoke.py`，
本轮新增 [13] 组「结构化字段契约、规则校验与人工审核闭环」）；界面截图 **24 张**、Markdown 文档 **22 份**（`docs/` 下 21 份 + 根目录 README；新增 `docs/codearts_prompts_advanced.md`）。
评测语料为构造集 24 + 留出 8、真实采集集 42 份 / 7 栏目；双集指标见 `docs/evaluation_result.md`、
`docs/holdout_result.md`，真实集分文体口径见 `docs/real_audit.md`。

CodeArts 配套资产说明：`codearts/` 下为提示词、留痕模板、填写示范与单页实操作战台
（`CodeArts实操作战台.html`），均不计入源码行数；`scripts/` 下的 `codearts_tools.py`、
`ci_gate.py` 已计入上述 Python 行数。`doctor` / `bootstrap` 两个子命令分别承担运行环境体检
与提交目录骨架生成，`11_CodeArts使用记录/` 位于比赛项目总目录，同样不计入源码统计。`codearts/prompts/` 下 11 份独立提示词由
`scripts/codearts_tools.py split` 从 `docs/codearts_prompts.md` 自动拆出（单一数据源），
`codearts/templates/` 下 5 份为留痕模板，`scripts/codearts_tools.py` 与 `scripts/ci_gate.py`
提供索引自检、交付件体检与构建门禁。**这些属于方案与工具，不构成 CodeArts 实操留痕**，
真实会话导出与七类截图仍需团队按 `docs/codearts_prompts.md` §4.2 的逐日排期执行后归档。

## 6. 性能与成本控制

- **解析结果缓存**：以 `sha256(标题+正文前800字+发布时间)` 为键缓存 24 小时，避免同一通知重复调用模型；
- **正文截断**：送入模型的正文上限 4000 字，超出部分不参与抽取（通知的关键信息通常在正文前 2/3）；
- **批量解析容错**：逐条 try/except，单条失败只记录到 `failed` 列表，不中断整批。
