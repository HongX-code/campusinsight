# 技术架构说明

## 1. 总体分层

系统为单体应用，四层结构，层间通过明确的函数边界交互，便于替换与单测。

| 层 | 职责 | 文件 |
| --- | --- | --- |
| 表现层 | 单页应用，REST 调用；Arctic Glass Design System（`app/static/css/style.css`）：7 视图、三档响应式，规范见 `docs/ui_design.md` | `app/templates/index.html`、`app/static/css/style.css`、`app/static/js/app.js`、`docs/ui_design.md` |
| 接口层 | 参数校验、路由、错误映射 | `app/routers/*`、`app/serializers.py` |
| 服务层 | 采集、清洗、抽取、匹配、问答、字段契约与规则校验 | `app/services/*` |
| 数据层 | ORM 模型、连接、建表 | `app/database/*` |

解析链路的服务模块（本轮补齐的三个模块列在最后三行）：

| 模块 | 职责 |
| --- | --- |
| `services/extractor.py` | 日期打分选截止、对象归一化、条件原子化、材料条目化 |
| `services/analyzer.py` | 解析编排、`_attach_literal_fields()` 挂载确定性字段、`_finalize()` 统一校验出口 |
| `services/matcher.py` | 可解释的三级结论与专业 / 年级硬条件冲突判定 |
| `services/genre.py` | 文体判别：事务通知 / 公示公告 / 新闻资讯 |
| `services/fields.py` | **结构化字段契约**：`FIELD_KEYS` 六个字面事实字段的确定性抽取，逐字段附原文 evidence |
| `services/reltime.py` | **相对时间解析**：`resolve_relative()` 结合发布时间把「本周五前」换算为 ISO 日期 |
| `services/validator.py` | **规则校验**：`audit()` 执行 C1—C9，输出 `{passed, issues, warnings, ok}` |

采集子层独立于解析链路，两者只通过"一条通知的 {title, content, publish_time}"交接：

| 模块 | 职责 |
| --- | --- |
| `services/collector.py` | 采集引擎：请求层（重试/编码/体积限制）、列表页解析、翻页、详情解析、附件抽取、栏目编排 |
| `services/crawler.py` | 单篇入口：用户粘贴一个链接时走这里，内部复用 collector 的请求与解析 |
| `services/genre.py` | 文体判别：事务通知 / 公示公告 / 新闻资讯，决定要不要抽报名类字段 |
| `scripts/real_audit.py` | 真实集质量审计：按文体分层复算指标，生成 `docs/real_audit.md` |
| `config/sources.json` | 采集源与选择器配置，新增高校只改配置 |
| `routers/sources.py` | 采集中心接口：源列表 / 抓取预览 / 勾选入库 |
| `scripts/crawl.py` | 命令行采集，支持落 JSON 快照（离线复现与举证） |

## 2. 关键数据流

### 2.1 采集 → 预览 → 入库

```
config/sources.json
   ↓ collector.crawl_source()
列表页 fetch_page → parse_list（配置选择器 / 结构打分兜底）
   ↓ parse_pagination()（只认真实链接，同目录才算翻页）
详情页 parse_detail（正文容器优先级 + 块级换行 + 数字碎片回粘）
   ↓ _extract_attachments()（正文内 + 附件区 + 全页）
{title, url, publish_date, content, attachments, content_type, chars}
   ↓ POST /api/sources/preview（标注 duplicate，不入库）
人工勾选 → POST /api/sources/import
   ↓ content_hash + source_url 双闸去重
notices(ingest_mode='crawl') → 解析链路（见 2.2）
```

采集与解析**解耦**：采集只负责"拿到干净正文"，解析只负责"读成结构"。
这样站点改版时只动 `config/sources.json`，抽取规则失效时只动 `extractor.py`，两边互不牵连。

### 2.2 录入 → 解析

```
用户提交 / URL 采集 / 栏目批量采集          ← 采集
   ↓
cleaner.clean_text()          归一化、去导航噪声、合并断行、保留章节标题
   ↓
genre.detect()                文体判别（闸门）：新闻资讯 → 不抽办理类字段（硬办理信号一票否决）
   ↓                          事务通知 / 公示公告 → 继续
classifier.classify()         词典加权打分 + 文体/志愿信号纠偏  → 分类 + 置信度
   ↓
extractor.extract()           抽取（含确定性字段）：日期打分选截止、对象归一化、条件从句、材料条目
   ↓                          ├─ fields.extract_structured()：年级 / 专业限制、报名开始、
   │                            活动举办时间、地点、联系人 / 电话 / 邮箱（字面事实，逐字段附 evidence）
   │                          └─ reltime.resolve_relative()：「本周五前」「三个工作日内」结合
   │                             publish_time 换算；缺发布时间则置空并标记待复核
   ↓
analyzer.analyze()            ① 大模型可用 → 提示词解析 → _validate_llm 校验
                              ② 不可用/失败 → _rule_result 规则结果
                              两条链路都过 _attach_literal_fields() 与 _apply_genre_gate()
   ↓                          —— 以上为「四层保护」：结构 / 文体 / 事实 / 兜底 ——
   ↓
_finalize()                   统一规则校验出口：validator.audit() 跑 C1—C9
   ↓                          硬异常进 issues → needs_review=true；软提示进 warnings
   ↓                          校验报告写入 result["checks"]
   ↓
notice_analysis 落库          14 类结构化字段 + evidence + deadline_source + checks
   ↓                          + confidence + needs_review + engine + genre + actionable
   ↓
人工审核（三态）             详情抽屉「规则校验与人工审核」区：通过 / 修正字段 / 驳回重解析
   ↓
展示                          字段 → 原文依据 → 校验报告逐条可见
```

文体闸门放在抽取之前、同时约束规则与模型两条链路，是为了避免"换上 MaaS 后同样的误报重现"。
下游也据此收敛：新闻稿不进入个性化匹配，待办接口直接返回 400。

确定性字段与大模型解耦：年级 / 专业限制、报名起止、活动举办时间、地点、联系方式这类**字面事实**
只由 `fields.py` 从原文捕获，不交给生成式模型输出；`_attach_literal_fields()` 挂载前逐条做证据接地校验，
证据对不上原文就整字段置空（宁缺勿造）。四层保护之外，`_finalize()` 是规则与大模型两条链路共享的
**统一校验出口**，任何链路都绕不过 C1—C9（详见第 5 节）。

### 2.3 匹配

```
用户画像(年级/专业/兴趣) + 全部已解析通知
   ↓ matcher.match_one()
截止时间 → 适用对象 → 专业限制 → 资格条件 → 兴趣方向
   ↓              └─ 专业 / 年级 / 学历硬条件改由 _check_major_hard() / _check_grade_hard()
   ↓                 读结构化枚举判定；明确冲突直接判 level="no"（暂不符合）
score(5-98，规则加权匹配度 · 非录取概率) + level(match/maybe/no) + reasons[]
```

匹配是纯规则运算，不调用模型：**结论必须可解释、可复现**。模型只负责把通知读成结构，判断逻辑留在代码里。
本轮把专业、年级、学历三类硬条件从"短字符串包含猜"改为读 `grade_requirement` / `major_requirement`
归一化枚举做冲突判定（`_check_grade_hard()` / `_check_major_hard()`）：命中冲突时不再给一个低分了事，
而是直接判 `level="no"`（暂不符合）并写明"通知限定 X，你当前为 Y"，避免把本不符合的通知包装成"可能符合"。

### 2.4 人工审核闭环

校验报告落库后，详情抽屉的「规则校验与人工审核」区（`.check-panel`）把它逐条展示出来：
通过 N 项 / 拦截 N 项 / 提示 N 项，并给出首个硬异常说明。`PUT /api/notices/{id}/analysis` 支持三态：

| 动作 | `action` | 行为 |
| --- | --- | --- |
| 通过 | `approve` | `reviewed=true`、`needs_review=false`，复核说明追加「人工通过」 |
| 修正字段 | （空，带字段） | 覆盖 `AnalysisUpdate` 中的结构化字段，标记「已人工复核」 |
| 驳回重解析 | `reject` + `reject_reason` | 回退 `reviewed=false`、`needs_review=true`，说明写「人工驳回：…（需重新解析）」 |

驳回不把错误结果洗成"已审核"；重新解析并再次通过时，旧的驳回说明会被清理，
避免说明里同时留着"需重新解析"和"已通过"。至此形成
**解析 → 规则校验 → 报告落库 → 人工三态 → 重新解析** 的闭环，界面截图见 `docs/shot-review.png`。

## 3. 三个核心设计决策

### 决策一：日期抽取用"上下文打分"而非"取第一个日期"

通知里通常有 3—6 个日期（发布时间、报名起止、活动时间、公示时间、评审时间）。取第一个或最靠后的都会错。

做法是给每个日期候选按左右 32 字窗口内的线索打分：

| 线索 | 权重 | 例 |
| --- | --- | --- |
| 报名截止 / 申请截止 | +6 | "报名截止：11月20日" |
| 截止 / 截至 | +4.5 | "截至11月7日18:00" |
| 范围结束符（至/到/—/~）出现在日期左侧 6 字内，**且上下文有办理动词** | +5 | "报名时间为11月1日**至**11月20日" |
| 前提交 / 前将 / 前发送 | +3.5—4 | "于11月6日**前将**材料交至…" |
| 发布时间 / 发布日期 / 印发 | −5—−8 | "**发布时间**：2026-10-15" |
| 举行 / 举办 / 开幕 / 讲座 | −2.5—−5 | "报告**时间**：11月10日" |

范围结束符这一条在接入真实站点后补了前置条件：原先"公示期为X至Y""新闻网讯 10月30日至11月2日"
同样会 +5，把公示期、会期、活动期全推成报名截止。现在要求该范围所在行（含上一行标签）
出现报名/申报/提交/征集等办理动词，且不含公示期/会期/新闻导语等排除词；标签独占一行时语境向前多取一行。
这一处修正让开发集截止日期准确率 91.7% → 100%、召回 90% → 100%。

取最高分；同分取较晚日期（范围区间的右端才是截止）。得分 ≤ 0 则判定"未识别到截止日期"，而不是硬猜一个。

### 决策二：适用对象归一化为身份词

原始表述五花八门："全日制在校本科二年级以上（含二年级）学生""经学校认定的家庭经济困难的全日制本科在校生""2027届本科、硕士、博士毕业生"。

直接把这些句子当"适用对象"既不利于展示，也无法参与判断。系统将其归一化为最小身份词集合：`本科生 / 硕士研究生 / 博士研究生 / 专科生 / 毕业生 / 教师 / 师生 / 学生`。

归一化后，匹配逻辑只需判断"用户身份 ∈ 通知对象集合"，规则稳定且可解释；年级、专业等细分限制归入 `conditions`。

### 决策三：报名材料按"条目"抽取

早期版本用关键词命中（出现"报名表"就加一条），结果是"扫描通知附件中的二维码填写报名表"会被整句当成材料，而"国家奖学金申请审批表"因为词表里没有而漏掉。

改为条目抽取：

1. 先按章节切块，命中"材料 / 清单 / 附件"标题的整段纳入候选；
2. 括号注释、数量词（各一份、复印件、若干）、编号前缀先剥除；
3. 按顿号/逗号/和/及切分为条目；
4. 条目含动词（扫描、填写、发送…）或过长时，只取其中已知的材料名词；
5. 否则条目本身以"表/书/单/件/料/明/案/图/片/频/码/证…"结尾即认定为材料。

该调整把报名材料 F1 从 45.7% 提升到 85.7%。

## 4. 采集层：三个反直觉的实现细节

这三条都不是"设计得好"，而是"踩过坑之后不得不这样写"，也是接入真实站点后最先暴露的问题。

### 细节一：正文容器不能取"文字最多的那个"

多数教程式的正文抽取是"遍历所有 div，选文字最多的"。在校园 CMS 上这一定会错：
外层 `div.content` 把面包屑、「发布时间」、**浏览量**一起包进去，永远是最长的。

后果不是"正文多几行"这么简单——浏览量每次访问都自增，正文内容随之变化，
`content_hash` 每次都不同，同一条通知会被反复判为"有更新"。

现在的做法：按选择器优先级命中，命中的多个容器之间再用"包含关系 + 体量比"收敛：

```python
wrapped = any(node is not other and node in other.parents
              and text_len(other) < text_len(node) * 1.3
              for _, other in hits)
if wrapped:            # 它只是更精确容器的外层包装
    continue
```

### 细节二：数字不能在清洗阶段被当噪声删掉

CMS 常把数字、单位、日期分别包进 `<span>`，`get_text("\n")` 之后
「2025」「年11月20日」成了两行，「2」「人」也成了两行。
如果清洗阶段带一条"纯数字行是最长行/噪声行"的规则，这些数字会被静默删除，
原文变成「报名截止时间 2025年月日20:00」——截止日期整条消失，且没有任何报错。

修复分两步：`_node_text()` 只在 `<br>` 和块级标签处换行，行内元素直接拼接；
`_merge_fragments()` 再把残留的数字碎片粘回相邻行。

效果：正文数字不再残缺，截止日期恢复可抽取。真实集后来改用分文体口径衡量
（事务与公示类办理截止覆盖 20/24，新闻资讯误报 0/18），见 `docs/real_audit.md`。

### 细节三：翻页链接必须校验目录

「查看更多」在校园站点里既用于翻页，也用于跳到别的栏目。
如果只按文字匹配，「综合新闻」翻着翻着会漂到「理工资讯」，把无关通知收进来，
而每次请求都返回 200，日志上看不出任何异常。

规则：文案是「查看更多/更多」时，跳转目标必须与当前页**同目录**才算翻页；
另外对「下一页」等于当前页的情况直接判定到底，防止自环。

## 5. AI 可信性设计（四层保护）

| 层 | 机制 | 拦截的问题 |
| --- | --- | --- |
| 结构保护 | 强制 JSON Schema；分类枚举收敛（近义词映射回 9 类）；列表长度与类型校验；容错解析代码围栏 | 模型输出非 JSON、字段类型错乱、自造分类 |
| 文体保护 | `genre.detect()` 先判事务通知 / 公示公告 / 新闻资讯；判为新闻时报名类字段整体留空、`actionable=false`，规则与大模型两条链路共用这道闸门 | **「看起来合理、原文根本没说」的假字段**：把赛事会期、公示异议期、学科名词当成报名信息 |
| 事实保护 | `date_grounded()`：抽出的日期必须能在原文找到"YYYY年M月D日 / YYYY-MM-DD / M月D日"等形态；`evidence_grounded()`：证据片段前 8 字必须出现在原文 | **日期幻觉**、编造条件、编造材料 |
| 兜底保护 | 模型不可用/超时/异常 → 规则引擎；引擎来源写入 `notice_analysis.engine` 并在界面标注 | 服务不可用导致业务中断 |

事实保护命中时的处理不是"修正"，而是**置空 + 降置信度 + 标记待复核**：宁可少给字段，也不给错字段。
文体保护与前三层互补：前三层校验"抽出来的对不对"，文体层先问"这条通知该不该抽"。
42 份真实通知里，闸门在 18 份新闻稿上拦下 25 个假字段，误报率 0/18；
公示公告的日期不丢弃，只改标 `deadline_kind="异议截止"`，避免与报名截止混称。

**四层保护之外还有规则校验，统一表述为「四层保护 + 规则校验（C1—C9）」**——它不是并列的第五层，
而是对四层产出结果的再约束：四层管"模型输出能不能信"，规则校验管"结果本身是否自洽、是否 grounded 于原文"。
`services/validator.py` 的 `audit(result, text, publish)` 依次检查：

| 编号 | 检查项 | 处理 |
| --- | --- | --- |
| C1 | 日期格式与真实性 | 硬异常 |
| C2 | 截止 ≥ 发布时间 | 硬异常 |
| C3 | 报名起止顺序 | 硬异常 |
| C4 | 截止时间跨度合理（≤ 730 天） | 硬异常 |
| C5 | 证据片段原文接地 | 硬异常 |
| C6 | 截止日期原文可定位（相对时间换算走 `deadline_source="relative"`） | 硬异常，否则置空 |
| C7 | 活动时间与截止冲突 | 软提示 |
| C8 | 置信度偏低 | 软提示，不硬拦截 |
| C9 | 文体闸门字段泄漏 | 硬异常 |

返回值 `{passed, issues, warnings, ok}`：硬异常进 `issues` 并置 `needs_review=true`，软提示只进 `warnings`。
`analyzer._finalize()` 是规则引擎与大模型两条链路的**统一校验出口**，把整份报告写入 `notice_analysis.checks`，
换引擎不会绕过约束；前端 `.check-panel` 据此渲染通过 / 拦截 / 提示计数，并承接 2.4 的人工审核三态。

**界面层的可信性落点**：详情抽屉把 `checks` 报告渲染为 `.check-panel`（通过 / 拦截 / 提示计数 + 人工审核三态），
14 类字段与各自的「原文依据」绑定为一组 `.field-block`，避免证据块占整行打乱双列网格；
点击任一「原文依据」由 `jumpToEvidence()` 在通知原文中黄色高亮（`.content-box mark`）并滚动定位，
从而在界面上形成「AI 结论 → 结构化信息 → 原文证据」的完整闭环。设计变量、组件规范与截图检查要点见 `docs/ui_design.md`。

工程规模与验证口径：源码约 **14300 行**（Python 10400 + 前端 3858，其中 HTML 497 / JS 1765 / CSS 1596）、**34 个路由端点**
（含页面 `/` 与 `/api/health`，其中 JSON API 28 个）、**14 类结构化字段**（总控文档 8.2）、
文体 3 类、`deadline_kind` 7 类；端到端自检 **143 项全通过**（`tests/test_smoke.py`，

## 6. 性能与成本控制

- **解析结果缓存**：以 `sha256(标题+正文前800字+发布时间)` 为键缓存 24 小时，避免同一通知重复调用模型；
- **正文截断**：送入模型的正文上限 4000 字，超出部分不参与抽取（通知的关键信息通常在正文前 2/3）；
- **批量解析容错**：逐条 try/except，单条失败只记录到 `failed` 列表，不中断整批。

## 7. 部署拓扑（华为云）

```
                 ┌──────────────────────────┐
   Internet ────▶│ ECS / Flexus 应用服务器    │
                 │  uvicorn app.main:app     │
                 │  :8000                    │
                 └───────┬──────────┬───────┘
                         │          │
             ┌───────────▼──┐   ┌───▼──────────────┐
             │ RDS for MySQL│   │ DCS for Redis    │
             │ 业务数据      │   │ 解析结果缓存      │
             └──────────────┘   └──────────────────┘
                         │
             ┌───────────▼──────────────┐
             │ ModelArts Studio (MaaS)  │
             │ DeepSeek 等大模型服务      │
             └──────────────────────────┘
```

启动命令：本地 `python run.py`（默认监听 `127.0.0.1`，带启动前体检）；云端 ECS / 容器对外暴露时
才用 `uvicorn app.main:app --host 0.0.0.0 --port 8000`。`0.0.0.0` 是通配监听地址而非浏览器网址，
本机访问一律 `http://127.0.0.1:8000/`，云端访问公网 IP 或域名。
环境变量通过 `.env` 或容器环境注入，密钥不落代码。

## 8. 后续演进方向
