1. **"四、材料要求"单独占一行**是高校通知的普遍排版。按句号切分会把标题与条目分离，条目失去"这是材料清单"的上下文。引入章节切块后材料召回率一次性提升约 18 个百分点（v2→v3）。
2. **资格条件是"约束"而不是"句子"**。v4 之前把逗号切分出的整句当条件，精确率只有 44.8%——整句里混着主语、修饰和并列。改成按约束类型（规模/年级/成绩/经济/纪律/服从性）归一到原子表述后，F1 从 48.1% 升到 94.3%（v4→v5）。
3. **日期线索是行内局部的**。按固定字符数开窗会让上一行的"投稿截止"渗到下一行的"录用通知"上，这是 v6 之前把会议征稿的截止日判错的原因。
4. **v7 的全部改动都来自真实网页**（见第 5 节），在此之前，同一套规则在构造样本上已经跑满 100% 的分类准确率——真实数据才是有效的测试集。
5. **v8 再次印证这一点**：42 份真实网页里有 18 份是新闻稿，构造集里一份都没有。规则引擎原本会把"10月30日至11月2日"的赛事举办时间抽成报名截止、把学科名"材料"抽成报名材料，这类**在新闻稿上硬造字段**的错误，任何只在事务通知上调参的评测都发现不了（见 6.8）。

## 6. 开发过程中定位并修复的缺陷

### 6.1 问答检索缺相关性门槛

"量子计算机的超导材料怎么制备"曾命中含"材料"二字的高校通知并给出答非所问的回答。
修复方式：引入命中词数量与覆盖率双阈值，并把"最近/有哪些/怎么"等疑问填充词从检索词中剥离。

### 6.2 日期上下文跨行串味

通知中"投稿截止：2026年12月20日 / 录用通知：2027年1月25日 / 终稿提交：2027年2月10日"三行并列时，
窗口开到 32 字符会把上一行的"截止"计入下一行。修复为**行内取上下文**，并额外处理"标签独占一行"的排版（此时上溯一行）。

### 6.3 分类纠偏无视明确体裁

`心理健康`、`运动会` 等文体强信号原本无条件给"校园活动"加 40 分，导致"心理健康主题讲座"被判为校园活动。
修复为：纠偏只在"学科竞赛与文体活动存在歧义"时生效，讲座/志愿服务等明确体裁不再被覆盖。

### 6.4 泛称与具体层次重复计入

"全日制在校本科生、研究生"曾输出 `['本科生','学生']`——泛称"学生"与具体层次并存时属于冗余。
修复为：存在具体学历层次时剔除"学生/毕业生"，并把"博士研究生"先行折叠，避免被"研究生"规则二次命中。

### 6.5 正文里的数字被当成噪声删掉（真实站点暴露）

研究生院页面的正文是 `<span>2</span>人`、`<span>2025</span><span>年11月20日</span>` 这种结构，
`get_text("\n")` 之后数字独立成行，清洗时被判为噪声行删除。结果原文变成：

```
报名截止时间 2025年月日20:00
```

截止日期整条消失，且没有任何报错——这是最危险的一类缺陷：**不报错的错误答案**。
修复分两步：`_node_text()` 只在 `<br>` 与块级标签处换行；`_merge_fragments()` 把残留的数字碎片粘回相邻行。
真实集上可识别的日期片段从 7/42 恢复到 23/42；后续 6.8 进一步说明这 23 条里混着新闻稿的误报，
因此该数字**不再作为质量指标使用**，改以 5.3 节的分文体口径为准。

### 6.6 「1.思想品德优良」被当成章节标题

`blocks()` 用 `^\d{1,2}[、.．]` 判断章节标题，「二、选拔条件」下的条目「1.思想品德优良，身心健康；」
也被当成标题，导致整个"选拔条件"章节的正文被切走，条件抽取结果为空。
修复为：纯数字编号必须同时满足"≤15 字且不含句读标点"才算标题。

修复后，该通知的条件抽取从 `[]` 变为
`['身体健康', '80分', '70分', '425分', ...]`，与原文条件逐条对应。

### 6.7 材料词表的"泛义词"造成误抽

"比拼解决方案""XX方案"曾被当成报名材料（词表里有裸"方案"），
而"两份《承诺书》"因为数量前缀没剥掉，输出成"两份《承诺书"。
修复为：移除裸"方案"，只接受"2-4 字限定词 + 方案"（如"实践方案""实施方案"）；
剥离数量前缀；非词表命中的条目长度收紧到 10 字以内。

### 6.8 新闻稿被硬套报名类字段、公示期被当报名截止（真实站点暴露）

这是 42 份真实数据暴露出的**第 4 类、也是最严重的一类**缺陷，因为它产出的是「看起来完全合理、
但原文根本没说」的结构化字段，人工复核时最容易放过。

| 现象 | 原文 | 错误输出 | 根因 |
| --- | --- | --- | --- |
| 赛事举办时间变报名截止 | "10月30日至11月2日，第十五届竞赛在武汉举行" | `deadline=2026-11-02`，证据指向赛事会期 | `RANGE_END` 里"至/到"无条件 +5 分，不校验这是不是报名时间 |
| 公示期变报名截止 | "公示期为11月20日至11月24日" | `deadline=2026-11-24` | 同上，且没区分"异议截止"与"报名截止" |
| 学科名变报名材料 | "材料学科在 Nature 发表成果" | `materials=['材料']` | 材料词表命中裸词，无文体约束 |
| 论坛举办日期变截止 | "人力资源管理论坛在武汉举行" | 抽出论坛结束日 | 同第一行 |

修复分三层：

1. **文体闸门**（`services/genre.py`）：先判 `事务通知 / 公示公告 / 新闻资讯`。信号要求是可解释的——
   新闻侧看导语（新闻网讯/通讯员/摄影/编辑）、URL 栏目（`/zhxw/`、`/xsdt/`、`/lgzx/`）；
   事务侧看办理词（报名、申报、截止、提交、报送、请各、附件、联系人…）。
   **关键在于分离度**：24 条事务通知全部含两个以上办理词，18 条新闻稿一条都没有，17 条带新闻导语，
   所以判据不需要机器学习，也不会误伤构造集。判为新闻时，截止/对象/条件/材料/方式全部留空，
   并置 `actionable=false`，不进入个性化匹配与待办。
2. **范围加分语境校验**（`extractor._pick_deadline`）：`至/到/—/~` 的 +5 分必须同时满足
   「本行含办理动词」且「本行不含公示/活动/报道类范围词」。公示期不直接丢掉，而是保留日期
   并用 `deadline_kind="异议截止"` 标注语义，让前端能区分"报名要截止了"和"公示有异议期"。
3. **日期类型细分**：新增 `deadline_kind` 共 7 类，由证据文本判定，替代原来笼统的一个 `deadline` 字段。

**一次回归与修正**：加上语境校验后，开发集用例「二、报名时间 / 2026年11月3日至2026年11月20日」
标签独占一行，日期行的窗口里没有办理动词，区间加分被误归零，截止日错选成起始日。
把办理语境的查找窗口从"本行"向前扩一行后修复，开发集截止日期准确率 **91.7% → 100%**、
召回 **90.0% → 100%**，留出集保持 100%，真实集未带回任何误报。

量化收益：闸门在 18 份新闻稿上拦下 25 个假字段（涉及 14 份），新闻误报率 0/18；
同时把构造集里"公示期被当补报截止"这个一直没被发现的老问题一并修掉。

### 6.9 按设计文档补齐时新发现的三类语义缺陷（v1.3）

本轮不是单纯"加字段"，在把总控 8.2 的十四字段对照到代码时，又暴露出三类**不报错但含义错**的问题：

| 现象 | 根因 | 修复 |
| --- | --- | --- |
| `major_requirement` 把「每人限报一队」「届蓝桥杯全国软件」「学位授权学科」当专业 | 并列清单切词过宽，语境未限定 | 加 `MAJOR_VERB` / `NO_LIMIT` / `LIST_STOP` / `NARRATIVE` 与 `scoped_text()`，只认带明确后缀单元或 ≥3 项并列专名清单；真实集误报压到 1 条（原文确有专业清单） |
| `start_time` 实际抽的是「举行/举办」时间，却被当成报名开始 | 字段语义与设计文档错位 | 按总控 8.2 摆正：`start_time = registration_start`，另设 `event_time` 承接活动举办时间；前端标签同步改为「报名开始时间」「活动举办时间」 |
| 原文写「研究生」，年级限制被归一化成「硕士研究生」 | 约束语境误继承 `target` 的归一化值 | `fields._constraint_text()` 改用原文限制行与 `conditions`，保持原文粒度，避免误伤博士生 |

另修 3 个实现缺陷：并列专业清单前缀「专业包括」与后缀「等相关专业」未剥离导致 H05 漏抽（该轮 API 链路自检从 80/81 升到 81/81，现为 143 项）；
`extract_contact()` 生成器误写列表字面量触发 `TypeError`；联络方式证据改用原文连续行，避免拼装描述串无法接地。

### 6.10 全端点与浏览器巡检新发现的五类缺陷（v1.5）

巡检前服务层 81 项自检全绿，但 T8 在真实库副本上仍抓到会让用户直接卡住的问题——
这类缺陷的共同点是**用例没走到接口层或界面层就不会暴露**：

| 现象 | 根因 | 修复 |
| --- | --- | --- |

## 8. 结论

1. 核心业务闭环（采集 → 文体判别 → 解析 → 规则校验 → 匹配 → 问答 → 待办 → 人工审核）在**离线、无大模型密钥**条件下完整可用，**143 项自检全部通过**；
2. 开发集分类与截止日期均达 100%，适用对象 F1 91.2%、资格条件 94.3%、报名材料 94.5%，可直接支撑演示与人工复核流程；v1.3 新增字段不参与双集标注，五项指标保持不变即为无退化；
3. 留出集显示规则引擎的泛化边界：新体裁的条件召回仍有 80%，材料达到 92.3%，**这是本项目保留大模型通道的直接原因**；
4. 真实站点回归验证了采集引擎面对 7 种页面模板的鲁棒性（100% 抓取成功率），并累计暴露出 4 类构造样本测不出来的缺陷；按文体重算后，事务类办理截止覆盖 20/24，新闻稿报名类字段误报 0/18；
5. 防幻觉由**四层保护 + 规则校验（C1—C9）**共同承担，其中在真实语料上起关键作用的三类检查各有独立用例：字段级的原文接地校验、**文体级的"不该抽就整体留空"**，以及 v1.3 的**规则级 C1—C9 统一校验出口**（规则引擎与大模型两条链路共用）。字面事实字段由确定性抽取器捕获，不交给生成式模型；
6. 处理效率由脚本现场实测：单条解析中位数 1.86 ms、100 条 0.202 s、495.5 条/秒（本机一轮实测，复跑以报告为准）；人工阅读耗时未做真人实验，**不填效率提升百分比**；
7. 本轮完成 **Arctic Glass UI 全量重构**：新增智能工作台首页为默认视图、7 视图与三档响应式、三级可信链路的界面落点，**20 张界面截图全部通过版式检查**；界面规范见 `docs/ui_design.md`；
8. **v1.5 稳定性回归**：全端点 117 次请求 0 个 5xx / 0 条数据一致性告警，7 视图浏览器巡检 0 控制台错误 / 0 横向溢出；人工修正非法日期、删除关联数据、驳回语义、改正文后结论过期、问答 `top_k` 五类缺陷均已修复并固化为自检断言；
